# One parse/project seam for sheets; published templates never carry Keeper's Notes

REST, WebSocket, copy, import, and template-use share one Zod storage boundary and the same server projection helpers. **Published character templates** are Instance-wide, so they never include **Keeper's Notes**: the field is stripped on publish, update, and every read, not rejected and not campaign-scoped. **Derived values** stay on-disk compatibility caches and are projected at read; **current resources** are writes and are never overwritten by a projection, and a projection that would leave the schema is clamped into bounds. A live HP or hit-die patch is refused only if the patched fields are invalid or the patch introduces a new schema error — a legacy over-limit sheet stays playable at the table, while a REST save still requires a fully valid sheet. Blank required-name rows may appear in the editor and are omitted on save; Flexible add controls stop at the server limits. Custom sheet-header colours that fail WCAG AA 4.5:1 against the fixed light header text are rejected, not auto-adjusted; already-stored pale colours still load and fail the next save. Shadowrun 6e Characters remain readable, assignable, and deletable, but creation, templates, sheet edits, and live resource patches stay closed until the sheet and an attribution section exist. Shipped starter templates keep feature and skill names and drop rules prose; D&D SRD 5.1 creature seeding stays the attributed exception; Pathfinder, Call of Cthulhu, and Shadowrun are structure-only. A PR that adds rules prose does not merge without a section in `SRD_ATTRIBUTION.md`. We rejected campaign-scoping the character-template library, a second sheet-patch schema, persisting blank-row drafts, silently recoloring headers, leaving Shadowrun as an API preview, and rewriting template prose as "SRD-safe" in this effort.

**Status**: accepted
