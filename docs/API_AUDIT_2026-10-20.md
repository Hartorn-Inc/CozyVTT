# Audit API HTTP CozyVTT — 2026-10-20

Lecture seule. Aucun MCP n’a été mis en place. Sources : code Express, OpenAPI,
guide Markdown, client frontend, inventaire de routes, `spec-coverage.py`.

## TLDR

**L’API est assez disciplinée pour un inventaire automatique, pas assez
contractuelle pour générer du tooling MCP sans normalisation.**

| | |
| --- | --- |
| Verdict | Chemins OK. Contrats (Zod, statuts, query, erreurs) pas encore générables. |
| Routes | 161 Express = 161 OpenAPI. 138 appels `api.ts` dans le catalogue. |
| Tags | 21 tags, 1 par opération. 161 `operationId` camelCase uniques. |
| Guide | `docs/API_REFERENCE.md` : 84 headings, 77 routes omises **volontairement**. |
| Tests | 7 routes `UNTESTED`. Le reste a au moins un smoke HTTP. |
| Auth | Cookie `cozyvtt.sid` uniquement. Pas de clé, pas de bearer, pas de version. |

**Ne pas générer un MCP depuis le YAML tel quel.** Un générateur n’y verrait
pas les 401/403/413/503 globaux (prose seulement), enverrait des booléens
query au lieu de `'true'`, et exposerait restore / delete user / delete
campaign / orphaned-files comme des outils ordinaires. Un MCP agirait **en
tant que l’utilisateur** (session + MFA).

### Ce qui va

Montage unique (`createApp`), RBAC campagne lu depuis `:campaignId`, Zod sur
l’auth et une grande partie des CRUD, limiteurs câblés, uploads par magic
bytes, envelope `{ error, message, code? }`, CI qui bloque un chemin qui
dérive.

### Ce qui ne va pas (à corriger avant tooling)

**P0**

- Gates mot de passe / MFA admin **fail-open** sur erreur DB.
- `ASSET_UPLOAD_RATE_LIMIT` non numérique → `NaN` → limite d’upload coupée.
- OpenAPI = parité **méthode + chemin** seulement (`spec-coverage.py`).

**P1**

- 7 routes sans test HTTP (dont fin de session, invitations, token templates).
- Bodies sans Zod : `endSession`, `POST` maps, `PUT` users, rôle membre.
- Query répétée → 500 ; `%`/`_` LIKE non échappés ; flags boolean vs `'true'`.
- `POST /characters` ignore la compatibilité de système de jeu.
- `GET /assets/:id` n’utilise pas `canReadAsset` (orphelin CAMPAIGN ; désaccord
  métadonnées 403 vs octets 200).
- `{id}` polymorphe (37 chemins). POST/PUT souvent RPC (`/assign`, `/favorite`…).

**P2**

- Deux validateurs vibe. `campaignDMOrPlayer` jamais monté. Enveloppes
  invitations atypiques. `GET /api/config` tagué Health. Guide incomplet.

### Prochaine étape

Formaliser les règles du §7 (path params nommés, Zod ↔ `$ref`, 401/400/429
sur chaque opération, query `'true'`/`'false'`) **avant** d’écrire un serveur
MCP. Source générable : `backend/docs/API_DOCUMENTATION.yaml`, pas le guide.

Le détail, les preuves `fichier:ligne` et les priorités suivent.

## Résumé exécutif

L’API REST/Express est globalement bien structurée et fortement instrumentée :

- 161 routes sont montées par `createApp`, et l’inventaire OpenAPI en décrit
  exactement 161.
- Les 138 appels détectés dans `frontend/src/services/api.ts` sont présents
  dans l’OpenAPI.
- Le guide humain est volontairement partiel : 84 routes y sont expliquées et
  77 routes restent hors de son périmètre déclaré.
- Les contrôles de scripts passent : `python3 scripts/spec-coverage.py` retourne
  zéro erreur et `python3 -m unittest discover -s scripts/tests` passe 21 tests.

Les écarts prioritaires avant tout futur tooling sont toutefois réels :

1. deux gates de sécurité (`mustChangePassword`, MFA administrateur) sont
   explicitement fail-open lors d’une erreur de lecture DB ;
2. le limiteur d’upload accepte une valeur d’environnement non numérique qui
   peut désactiver sa limite ;
3. des erreurs multipart connues sur l’import UVTT et la restauration tombent
   encore sur un 500 générique ;
4. sept routes sont déclarées mais sans test envoyant une requête ;
5. la parité OpenAPI/client est principalement une parité de chemins et de
   méthodes, pas une comparaison de contrats runtime ;
6. plusieurs appels HTTP et constructeurs d’URL frontend ne passent pas par les
   appels analysés par `scripts/spec-coverage.py`.

### Paramètres de chemin et méthodes

Les paramètres de chemin ne sont pas un vocabulaire unique. `{id}` apparaît
sur 37 chemins et désigne tour à tour un user, une invitation, un
personnage, un asset, une carte, un token template, un character template
ou un admin-user. Les noms plus précis existent déjà ailleurs
(`campaignId`, `creatureId`, `tokenId`, `lightId`, `macroId`, `noteId`,
`sessionId`) et dans `components.parameters` (`CampaignId`, `MapId`,
`CharacterId`, …) — mais `MapId` s’appelle toujours `id` dans le chemin
(`backend/docs/API_DOCUMENTATION.yaml:11334-11341`). `{sid}` pour un mur
n’a pas d’équivalent lisible.

Méthodes : 63 GET, 52 POST, 24 PUT, 19 DELETE, 3 PATCH. Une trentaine de
chemins sont des verbes RPC (`/login`, `/assign`, `/copy`, `/set-current`,
`/tokens/move`, `/favorite` qui toggle, `/sessions/.../end`, `/from-token`,
`/copy-to/{targetCampaignId}`, …). Ce n’est pas bloquant pour un générateur
si chaque opération a un `operationId` et un résumé, mais ça empêche de
déduire automatiquement « POST = create, PUT = replace ».

Sécurité OpenAPI : 12 opérations publiques (`security: []`), les 149 autres
déclarent `cookieAuth` (cookie `cozyvtt.sid`). Le schéma d’erreur partagé
dit explicitement que `error` n’est pas un identifiant stable, et que le
client doit brancher sur HTTP + `code` quand il existe
(`backend/docs/API_DOCUMENTATION.yaml:12660-12681`). Codes machine
documentés : `PASSWORD_CHANGE_REQUIRED`, `MFA_ENROLMENT_REQUIRED`,
`SIGN_IN_EXPIRED`, `CHARACTER_CHANGED`, `ASSET_IN_USE`,
`UVTT_IMPORT_NEEDS_CONFIRMATION`.

Complétude des réponses OpenAPI (confirmé par parsing YAML) :

- 401 documenté **par opération** sur 63 / 149 routes authentifiées
  (88 manquent localement). Ce n’est pas un oubli total : le YAML le
  décrit une fois pour toutes dans `info.description`
  (`backend/docs/API_DOCUMENTATION.yaml:166-188`). Un générateur OpenAPI
  strict (MCP, client SDK) ne lira **pas** cette prose et croira que
  `GET /api/campaigns` ne peut répondre que 200.
- 500 documenté sur 45 / 161 ;
- 429 documenté sur 20 opérations (les limiteurs dédiés), jamais le
  limiteur général `/api` de 300 req/min ;
- 400 absent de 22 mutations **sans** `requestBody` (DELETE, seed,
  favorite, set-current) — acceptable. Toute mutation JSON avec body a
  un 400 explicite, **sauf** le cas `endSession` dont le body n’est pas
  validé par Zod (`backend/docs/API_DOCUMENTATION.yaml:4426-4461`).

32 schémas réutilisables existent sous `components.schemas`. Beaucoup de
corps de requête restent inlinés dans l’opération. 5 opérations
multipart (`upload`, documents, import/preview, restore, UVTT).

`backend/src/app.ts:75-259` est la source d’assemblage commune au serveur et
aux tests. L’ordre est explicite :

1. Helmet et CORS ;
2. vérification d’origine ;
3. parsing JSON limité à 1 Mo ;
4. restore gate avant la session ;
5. session ;
6. setup gate ;
7. health check ;
8. limiteur général `/api` ;
9. gates de changement de mot de passe et MFA administrateur ;
10. routeurs ;
11. 404 JSON ;
12. error handler.

`backend/src/__tests__/appAssembly.e2e.test.ts:130-175` verrouille cet ordre,

### Authentification et autorisation côté serveur

`backend/src/middleware/auth.ts:35-88` partage la notion de session signée
entre `requireAuth`, `requireAdmin` et `requireRole`, y compris la fin de
session après la durée maximale de connexion. Les gardes de campagne sont
composées dans `backend/src/middleware/compose.ts:18-43` et réévaluent le
membership en base dans `backend/src/middleware/rbac.ts:35-88`.

`campaignRoleGuards.e2e.test.ts:170-238` compare les gardes réellement attachées
aux  routes avec une matrice DM/membre et exerce les refus 401/403. C’est une
bonne protection contre l’ouverture accidentelle d’une nouvelle route de
campagne.

### Validation et bornes

Les validateurs partagés évitent plusieurs copies divergentes :

- auth et MFA : `backend/src/validators/auth.ts:18-90` ;
- campagnes : `backend/src/validators/campaigns.ts:8-90` ;
- personnages : `backend/src/validators/characters.ts:8-31` ;
- documents : `backend/src/validators/documents.ts:20-70` ;
- token shapes : `backend/src/validators/tokens.ts:40-230` ;
- créatures et token templates : `backend/src/validators/creatures.ts:20-60`
  et `backend/src/validators/tokenTemplates.ts:12-62`.

Le body vide est normalisé par
`backend/src/middleware/bodyParsers.ts:26-39`, et
`requestWithoutBody.e2e.test.ts:38-55` vérifie que les handlers répondent 400
plutôt que 500.

### Uploads et réponses d’erreur

Les uploads contrôlent les magic bytes, le type déclaré, la taille et
l’extension stockée dans `backend/src/middleware/fileValidation.ts:70-170`.
Les fichiers et thumbnails sont supprimés sur les chemins d’échec dans
`backend/src/routes/assets.ts:420-530`. Les tests de multipart malformé lancent
un vrai processus et vérifient que le serveur survit
(`malformedUpload.e2e.test.ts:70-150`, `:330-367`).

`backend/src/middleware/errorHandler.ts:20-80` évite de renvoyer en production
les messages d’exception pouvant contenir un chemin, une URL DB ou un secret.
Les erreurs JSON invalides et les corps trop larges ont des réponses dédiées.

### Rate limits et parité de limites

Le limiteur général est monté avant tous les routeurs et le test de câblage
vérifie son emplacement et ses 300 requêtes/minute
(`limiterWiring.e2e.test.ts:230-267`). Les limiteurs spécialisés sont listés
dans `ROWS` et testés sur les routes réelles
(`limiterWiring.e2e.test.ts:100-230`). Le test de validation IPv6 et de
`ipKeyGenerator` complète cette couverture
(`rateLimitValidation.test.ts:40-90`, `rateLimiters.test.ts:200-237`).

### Documentation avec garde-fous

L’OpenAPI indique explicitement qu’il s’agit d’une surface interne sans garantie
de compatibilité (`backend/docs/API_DOCUMENTATION.yaml:1-35`). Le script de
couverture refuse les chemins dynamiques indécidables et les routeurs montés
dans une forme qu’il ne sait pas lire
(`scripts/spec-coverage.py:88-150`). Les tests documentaires vérifient aussi
les routes citées dans la prose OpenAPI
(`backend/src/__tests__/documentedFacts.test.ts:425-453`).

## 4. Constats classés par criticité

### Criticité élevée — gates de compte fail-open lors d’une panne DB

**Statut : confirmé dans le code ; effet opérationnel non reproduit ici.**

`requirePasswordChanged` lit le flag en base pour les anciennes sessions, puis
attrape toute erreur DB et retourne `false`, ce qui laisse passer la requête :
`backend/src/middleware/passwordChange.ts:40-66`.

`requireAdminMfa` fait de même : son `catch` journalise l’erreur puis appelle
`next()`, donc une erreur de lecture de la politique MFA ne bloque pas
l’administrateur : `backend/src/middleware/adminMfa.ts:43-66`.

Le commentaire explique le choix de ne pas bloquer tous les administrateurs,
mais le résultat est une décision de sécurité fail-open. Le cas est plus
limité pour le mot de passe quand la session contient déjà le booléen, mais il
reste possible pour les sessions anciennes. Pour MFA administrateur, la lecture
est effectuée à chaque requête d’admin.

**Priorité : P0 avant tooling de sécurité.** Formaliser une politique unique :
soit refuser en 503 avec une erreur explicite de dépendance indisponible, soit
limiter strictement le fail-open à un état de session déjà vérifié et daté.
Ajouter des tests simulant une panne DB dans les deux gates.

### Criticité élevée — limiteur d’upload configurable sans validation positive

**Statut : confirmé dans le chemin de code ; désactivation effective à
reproduire avec une variable invalide.**

`uploadLimiter` fait `max: parseInt(process.env.ASSET_UPLOAD_RATE_LIMIT || '30')`
et contient lui-même le TODO indiquant qu’une valeur non numérique produit
`NaN` et désactive la limite :
`backend/src/routes/assets.ts:53-72`.

Le limiteur général utilise au contraire `positiveIntegerFromEnv`, ce qui montre
que le projet dispose déjà de la stratégie correcte (`backend/src/app.ts:65-73`).

**Priorité : P0.** Partager le parseur positif, refuser le démarrage ou appliquer
le défaut sur toute valeur invalide, et ajouter un test avec `0`, négatif,
décimal, texte et valeur vide. Documenter si une limite `0` est interdite ou
signifie un blocage total.

### Criticité moyenne — erreurs multipart connues répondues en 500

**Statut : confirmé par le test et le commentaire du test.**

Le test de bodies multipart malformés documente explicitement que les routes
UVTT et restore laissent certaines erreurs au handler générique, qui répond
500, alors qu’il faudrait répondre 400 :
`backend/src/routes/__tests__/malformedUpload.e2e.test.ts:350-367`.

Le handler générique reconnaît seulement `entity.too.large` et
`entity.parse.failed`; les erreurs `charset.unsupported` et
`encoding.unsupported` tombent encore dans le 500
(`backend/src/middleware/errorHandler.ts:38-46`).

**Impact :** une entrée contrôlable par le client apparaît comme une panne
serveur, pollue les logs d’erreur et complique les clients/MCP qui doivent
distinguer retryable/server de malformed/client.

**Priorité : P1.** Centraliser la traduction des erreurs multipart/parser :
400 pour body malformé ou encodage non supporté, 413 pour taille, 415 pour
media type/charset quand applicable, et tests exacts de statut et de forme pour
chaque upload.

### Criticité moyenne — une route sensible est volontairement sans validation de body

**Statut : confirmé et explicitement documenté.**

`PUT /api/campaigns/:campaignId/sessions/:sessionId/end` lit directement
`saveState` et `notes`, applique une coercition truthy et coupe `String(notes)`
à 2 000 caractères : `backend/src/routes/campaigns.ts:2047-2088`.

L’OpenAPI reconnaît elle-même que « The body is not schema-validated » et décrit
les valeurs truthy : `backend/docs/API_DOCUMENTATION.yaml:4416-4461`.
La route est aussi l’une des sept routes de `UNTESTED`
(`backend/src/routes/__tests__/routeInventory.test.ts:181-190`).

**Risque :** le contrat accepte silencieusement des types que le schéma
OpenAPI présente comme booléen/string ; un client peut envoyer un objet, un
tableau ou `"false"` et obtenir un comportement différent de son intuition.

**Priorité : P1.** Introduire un schéma (`saveState` booléen, `notes` texte
borné), choisir explicitement si l’ancien comportement permissif doit être
conservé, puis ajouter les cas 400/200 et les tests de concurrence/fin déjà
terminée.

### Criticité moyenne — parité OpenAPI limitée au chemin et à la méthode

**Statut : confirmé par l’implémentation des scripts.**

`spec-coverage.py:225-238` extrait uniquement les couples méthode/chemin de
l’OpenAPI. `main()` compare ensuite les ensembles de routes et vérifie les
appels détectés du client (`scripts/spec-coverage.py:270-310`), mais ne compare
pas :

- les schémas de requête avec les validateurs Zod ;
- les statuts réellement émis ;
- les noms et formes de réponses ;
- les règles d’authentification/RBAC ;
- les limites et headers de rate limit ;
- les exemples avec une réponse runtime.

Le test de formes du guide compare seulement les champs montrés dans sept
exemples, et autorise des réponses réelles plus riches
(`apiReferenceShapes.e2e.test.ts:50-68`).

**Impact :** un chemin peut rester parfaitement paritaire alors que son body,
son statut ou sa permission dérive. C’est le principal angle mort à traiter
avant de transformer l’API en outil consommable.

**Priorité : P0 pour le futur contrat MCP.** Définir un format de contrat
machine-readable par opération : méthode, chemin, auth policy, paramètres,
body, réponse par statut, erreurs et idempotence. Générer ou vérifier ce
contrat depuis les validateurs/runtime, plutôt que d’ajouter seulement un
second parseur de chemins.

### Criticité moyenne — sept routes sans test HTTP de requête

**Statut : confirmé et assumé par une liste de gaps.**

Les sept routes non testées sont celles de l’inventaire chiffré ci-dessus.
Certaines sont particulièrement sensibles :

- `GET /api/auth/registration-status` est public ;
- `GET /api/invitations` et `POST .../decline` ont un contrat d’erreur
  différent ;
- les trois token-template writes manquants portent sur des données privées
  au DM ;
- la fin de session porte une mutation d’état et n’a pas de schéma de body.

Le mécanisme d’inventaire est bon, mais la règle actuelle permet à ces gaps de
rester durables. **Priorité P1 :** réduire `UNTESTED` à zéro avant d’exposer une
surface automatisée, avec au minimum auth, validation, succès et refus
d’autorisation par famille.

### Criticité moyenne — recherches et query params non normalisés

**Statut : confirmé par plusieurs TODOs de production.**

Quatre listes transmettent directement des motifs `%` et `_` à la recherche
PostgreSQL :

- assets : `backend/src/routes/assets.ts:220-223` ;
- creatures : `backend/src/routes/creatures.ts:145-148` ;
- token templates : `backend/src/routes/tokenTemplates.ts:40-44` ;
- character templates : `backend/src/routes/characterTemplates.ts:196-198`.

Le résultat est une recherche plus large que la chaîne demandée et peut générer
des scans coûteux. La route d’invitation utilise déjà
`escapeLikePattern` (`backend/src/routes/campaigns.ts:730-750`), donc une
convention existe.

Les répétitions de paramètres arrivent aussi en tableau et peuvent provoquer un
500 sur les listes d’assets et de créatures :
`backend/src/routes/assets.ts:180-183` et
`backend/src/routes/creatures.ts:115-120`.

**Priorité P1 :** parseur commun de query scalar/enum/pagination ; répétition
refusée en 400 ; échappement LIKE partagé ; tests `%`, `_`, tableau, nombre
négatif, NaN et limite supérieure.

Les flags query sont aussi **typés boolean dans l’OpenAPI et lus comme
chaînes** dans Express :

| Paramètre | OpenAPI | Runtime |
| --- | --- | --- |
| `includeAudio` | boolean | `=== 'true'` (`campaigns.ts:2219`) |
| `includeTokens` | boolean | `!== 'false'` (défaut vrai, `:2220`) |
| `usable` | boolean | chaîne via axios |
| `force`, `mine` | `enum: ['true']` | `=== 'true'` — le modèle honnête |

Un générateur qui sérialise `true` en `1` ou `True` changerait le contenu
d’un export sans erreur. Aligner toute la spec sur `enum: ['true']` (ou
parser boolean de façon unique). Un `campaignId` multipart répété à
l’upload n’est pas refusé et peut 500 (`assets.ts:393-398`).

Le LIKE `%`/`_` n’est **pas** une injection SQL (requêtes paramétrées) ;
l’impact est un élargissement de recherche, pas une lecture hors politique.

### Criticité moyenne — création d’un personnage dans une campagne avec système incompatible

**Statut : confirmé et explicitement signalé dans le code.**

`POST /api/characters` vérifie le membership mais ne compare pas le
`gameSystem` envoyé au système de la campagne lorsqu’il est fourni :
`backend/src/routes/characters.ts:145-170`.

Le commentaire indique que la route peut créer un personnage Pathfinder dans
une campagne D&D, alors que l’assignation et l’acceptation d’invitation refusent
ce cas. C’est une incohérence de contrat entre trois chemins de création.

**Priorité P1 :** appeler la même fonction `systemsCompatible` sur create,
assign et accept ; documenter la même erreur 400 ; tester les quatre
combinaisons typed/flexible.

### Criticité moyenne — sémantique d’accès assets non uniforme

**Statut : confirmé ; intention à décider.**

Les routes de fichiers n’emploient pas toutes la même stratégie de
non-divulgation :

- document et audio répondent 404 si le caller ne peut pas lire ;
- map, token, métadonnées et téléchargement répondent 403 dans plusieurs cas.

Par exemple, `GET /api/assets/:id` rend 403 pour un asset USER/CAMPAIGN non
accessible (`backend/src/routes/assets.ts:545-600`), alors que les documents
utilisent 404 (`:997-1015`) et l’audio 404 (`:1173-1195`). Le même fichier
contient un TODO sur un asset CAMPAIGN dont la campagne a été supprimée
(`backend/src/routes/assets.ts:572-576`).

L’OpenAPI dit explicitement que la route de métadonnées a ses propres règles
(`backend/docs/API_DOCUMENTATION.yaml:5556-5565`), ce qui rend l’écart
documenté mais pas nécessairement souhaitable.

L’inverse existe aussi : un asset USER utilisé sur la carte courante peut
être **lu en octets** (`canReadAsset` → 200 sur `/maps/:id`) et **refusé en
métadonnées** (403 sur `GET /:id`). Un outil `get_asset` et un outil
`get_map_image` ne seraient pas d’accord sur le même UUID.

Les 403 maps/tokens/download/métadonnées vs 404 documents/audio forment un
oracle d’existence pour qui possède déjà l’id. `GET /api/users/:id` refuse
403 **avant** le lookup (`users.ts:67-72`) : c’est le modèle à copier, ou
le 404 masqué des documents.

**Priorité P1 :** décider par classe de ressource si l’existence d’un UUID est
masquée ; réutiliser des fonctions d’accès et un mapping de statut unique pour
metadata/download/inline.

### Criticité moyenne — 304 de document sans CSP sandbox

**Statut : confirmé par un TODO de production.**

Pour un document texte inchangé, `GET /api/assets/documents/:id` répond 304 avant
d’avoir ajouté la CSP `default-src 'none'; sandbox`
(`backend/src/routes/assets.ts:1044-1057`). Le code précise lui-même ce risque.

**Priorité P1 :** poser les headers de réponse documentaire avant toute branche
304, puis tester 200 et 304 avec contrôle de `Content-Security-Policy`,
`Content-Type`, `ETag` et `X-Content-Type-Options`.

### Criticité faible à moyenne — client UVTT hors base API et refus non affiché

**Statut : confirmé par le code frontend et son TODO.**

`getExportUVTTUrl` annonce utiliser la base API mais renvoie une URL relative :
`frontend/src/services/api.ts:995-1001`. À l’inverse, `getAssetUrl` et
`getAssetDownloadUrl` préfixent `API_BASE_URL`. Sur un déploiement avec
`VITE_API_URL` distinct, l’export UVTT peut viser l’origine frontend au lieu de
l’API.

De plus, `MapManager` déclenche un lien `<a>` vers l’export ; son `try/catch`
ne peut pas intercepter un 422 HTTP. Le TODO le constate :
`frontend/src/components/campaign/MapManager.tsx:376-395`.

**Priorité P1 pour le client automatisé :** centraliser les constructeurs d’URL,
inclure l’encodage des IDs, et utiliser un fetch contrôlé pour ne créer le
download qu’après un 200, afin de restituer les erreurs 422/403/404.

### Criticité moyenne — deux validateurs vibe qui divergent

**Statut : confirmé, TODO dans le code.**

`PUT /api/campaigns/:campaignId/vibe` appelle `validateVibeSettings`
(`backend/src/utils/vibe-presets.ts:91-100`) ; `PUT /api/campaigns/:campaignId`
passe par `VibeSettingsSchema` (`backend/src/validators/campaigns.ts:69-85`).
Un nom de période peut faire 50 caractères d’un côté et 100 de l’autre ;
seul le premier exige `enabled`, au moins une période et des noms uniques.

**Priorité P1 :** un seul schéma Zod partagé, utilisé par les deux routes
et par l’import.

### Criticité faible — GET `/api/setup/status` peut écrire

**Statut : confirmé.**

`setupState()` (`backend/src/services/systemSettings.ts:72-82`), appelé par
ce GET et par le setup gate, marque `setupCompleted` si un administrateur
existe déjà mais que le flag n’a jamais été posé. Documenté dans l’OpenAPI
(`getSetupStatus`, lignes 390-395). Pour un outil, ce n’est pas une lecture
pure : idempotence à déclarer, pas à relancer en boucle sans le savoir.

### Criticité faible — garde composée jamais montée

**Statut : confirmé.**

`campaignDMOrPlayer` est exporté (`backend/src/middleware/compose.ts:45`) et
documenté dans `docs/ARCHITECTURE.md` et `backend/RBAC_QUICK_REFERENCE.md`,
mais aucune route ne l’attache. Les mises à jour de token joueur passent par
`campaignMember` + `canControlToken`. Une génération qui lirait le guide RBAC
inventerait une politique que le serveur n’applique pas.

### Criticité faible — deux ressources « templates »

`GET /api/characters/templates/:gameSystem/:templateName` (presets compilés)
et `/api/character-templates` (feuilles publiées) coexistent. L’`operationId`
les distingue (`getBuiltInCharacterTemplate` vs `listCharacterTemplates`) ;
un humain ou un LLM qui ne lit que le chemin les confondra.

### Criticité faible — formes d’erreur et réponse invitations atypiques

**Statut : confirmé et documenté comme exception.**

Les invitations renvoient une liste nue pour `GET /api/invitations` et
`message` seul pour plusieurs erreurs
(`backend/src/routes/invitations.ts:26-61`, `:90-106`, `:220-249`).
`docs/API_REFERENCE.md:1690-1706` avertit de cette exception.

Ce choix peut être maintenu pour compatibilité, mais il complique les clients
génériques et les futurs outils. **Priorité P2 :** normaliser vers
`{ data }`/`{ error, message, code? }`, ou déclarer explicitement une exception
stable dans le contrat machine-readable.

### Criticité faible — allowlists dupliquées entre les deux account gates

**Statut : confirmé.**

`passwordChange.ts:20-35` et `adminMfa.ts:28-40` gardent chacun une copie des
chemins autorisés, et le premier contient le TODO indiquant l’absence de
contrôle de parité. Une modification d’un gate peut donc rendre l’autre plus
strict ou plus permissif sans échec de test dédié.

**Priorité P2 :** partager une constante de politiques ou ajouter un test
`keepInStep` qui compare les deux ensembles avec la politique documentée.

### Criticité faible — warnings de descripteurs dans `spec-coverage.py`

**Statut : confirmé par l’exécution des tests de scripts.**

`scripts/spec-coverage.py:58` définit `read` avec `io.open(...).read()` sans
context manager. Les 21 tests passent, mais l’exécution produit des
`ResourceWarning` de fichiers non fermés.

**Priorité P2 :** utiliser `with io.open(...) as f`, ce qui est important pour
un outil appelé régulièrement par CI ou un serveur de tooling long-lived.

## 5. Hypothèses à vérifier séparément

Les points suivants ne sont pas affirmés comme vulnérabilités avérées :

- **Brute force setup :** `POST /api/setup/init` n’a pas de limiteur dédié ; il
  ne bénéficie que du limiteur général monté sur `/api`
  (`backend/src/app.ts:190-207`). Le token généré fait 16 octets aléatoires
  (`backend/src/services/setupToken.ts:18-31`), ce qui réduit fortement le
  risque pratique. Il faut décider si une limite dédiée est néanmoins requise
  pour le coût de parsing et la télémétrie.
- **Direct fetch frontend :** `DocumentReader.tsx:110-117` fait un `fetch`
  direct, et `MapManager.tsx:384-390` utilise un lien direct. Cela ne prouve pas
  une route non documentée, mais prouve que le périmètre actuel du script n’est
  pas exhaustif.
- **OpenAPI lint :** le YAML est parsé par le script, mais le résultat Redocly
  reste non vérifié dans cette session.
- **Fail-open en production :** le code confirme le comportement en cas
  d’exception DB ; l’occurrence et la durée d’une telle fenêtre dépendent du
  driver, du pool PostgreSQL et du déploiement.

## 6. Priorités de normalisation avant futur tooling MCP

### P0 — contrat et sécurité

1. Adopter une politique fail-closed explicite pour les gates de compte et
   tester les pannes de dépendances.
2. Valider positivement toutes les configurations de rate limit au démarrage.
3. Définir un contrat par opération couvrant méthode, chemin, auth/RBAC,
   paramètres, body, réponse par statut, erreurs, idempotence et effets
   asynchrones. L’`operationId` unique est déjà là ; il manque le lien
   Zod ↔ schéma OpenAPI et le 401/429/500 systématiques.
4. Étendre l’analyse des appels client à tous les `fetch`, clients HTTP,
   helpers qui construisent des URLs et liens de téléchargement, pas seulement
   les appels `this.client.*` dans `api.ts`.
5. Ne pas générer d’outils MCP depuis le guide Markdown : il est volontairement
   incomplet (84/161) et n’est vérifié que sur sept exemples.

### P1 — cohérence HTTP et couverture

1. Faire disparaître les 7 routes de `UNTESTED`.
2. Introduire un parseur commun pour body/query scalar, enums, pagination et
   répétitions.
3. Normaliser les erreurs parser/multipart en 400/413/415 et les réponses
   d’accès assets selon une politique 403/404 décidée.
4. Corriger les incohérences de validation :
   - fin de session ;
   - création de personnage dans une campagne ;
   - recherche LIKE et paramètres répétés ;
   - CSP sur 304.
5. Ajouter des tests de contrat générés ou vérifiés depuis l’OpenAPI pour
   chaque opération, plutôt que seulement des smoke tests de route.

### P2 — hygiène et ergonomie

1. Partager les allowlists des gates.
2. Fermer proprement les fichiers des scripts d’inventaire.
3. Uniformiser les enveloppes de réponse et d’erreur, ou formaliser les
   exceptions legacy.
4. Faire remonter au client les refus de download avant création d’un fichier.

## 7. Règles à formaliser pour un futur client/outillage

Avant toute génération de client ou outil MCP, la documentation de l’API
devrait imposer les règles suivantes. **Aucun serveur MCP n’a été ajouté
ici** ; ces règles sont le prérequis pour ne pas écrire le tooling à la
main plus tard.

Contrat OpenAPI (déjà partiellement en place) :

- Une opération = un `operationId` camelCase unique, un tag unique parmi
  la liste déclarée, un `summary`, une `description`. C’est déjà vrai pour
  161/161 ids et tags ; rester à cette barre.
- Un paramètre de chemin porte le nom de la ressource (`campaignId`,
  `characterId`, `mapId`, `assetId`), jamais un `{id}` polymorphe.
- Chaque opération authentifiée documente 401 ; chaque mutation avec body
  documente 400 ; le limiteur général documente 429 ou un `default`.
- Les schémas de body sont des `$ref` vers `components.schemas` alignés
  sur les schémas Zod du routeur (`safeParse` / `parseBody`). Pas de
  validation manuelle `typeof` / `String(x)` sur une route consommable.
- `error` n’est pas un identifiant ; `code` l’est, et la liste des codes
  est versionnée dans le schéma `Error`.
- Les exceptions d’enveloppe (`GET /api/invitations` liste nue, invitations
  `{ message }` seul, `GET .../characters/:id/validate` → `{ isValid, errors }`)
  sont soit normalisées, soit marquées `x-cozyvtt-envelope`.
- Le schéma `Error` doit aussi déclarer `setupUrl` (gate setup), `usage` /
  `omitted` (409 `ASSET_IN_USE`). Les réponses transverses (setup 403,
  restore 503, origin 403, 413) doivent être des `$ref` **sur chaque
  opération**, pas seulement de la prose dans `info.description`.
  `PasswordChangeRequired` existe déjà dans `components.responses` et n’est
  pas réutilisé globalement.
- Les query flags sont des chaînes `'true'`/`'false'`, jamais un boolean
  JSON. Uploads, archives, restore et flux binaires (export, backups, audio)
  restent hors outils « JSON-only ».

Comportement HTTP :

- Une route n’est consommable que si son auth policy et son scope de ressource
  sont explicites ; un rôle de plateforme ne vaut pas automatiquement rôle de
  campagne.
- Les réponses doivent être branchées sur le statut HTTP et, lorsqu’il existe,
  sur un `code` machine-readable ; le texte `message` est informatif.
- Un 400 représente une entrée invalide, un 401 une session absente/expirée,
  un 403 une permission refusée, un 404 une ressource absente ou masquée, un
  409 un conflit d’état, un 413 une taille dépassée, un 415 un format média
  refusé, un 422 une demande sémantiquement impossible, et un 5xx une panne
  serveur.
- Les retries doivent être autorisés uniquement pour les opérations dont
  l’idempotence est documentée. Les créations, emails, imports, restore et
  mutations de rôle ne doivent pas être relancés aveuglément.
- Les limites doivent être lues depuis les headers `Retry-After` et
  `RateLimit-*` quand elles existent ; une réponse 429 sans `Retry-After` doit
  être signalée comme refus d’opération concurrente, non comme simple quota.
- Les uploads doivent utiliser les noms de champs documentés, un seul fichier,
  les limites publiées et une gestion explicite des erreurs de parsing.
- Un outil ne doit jamais supposer que l’OpenAPI garantit la stabilité : le
  document affirme l’absence de versioning et de compatibilité
  (`backend/docs/API_DOCUMENTATION.yaml:1-35`).
- Les endpoints REST et les événements WebSocket doivent garder leurs règles de
  visibilité cohérentes ; une donnée filtrée dans le live path ne doit pas
  réapparaître non filtrée dans l’historique REST.

## Conclusion

La base actuelle est mature pour empêcher les dérives de chemins : montage
central, inventaire, parité OpenAPI/client, matrice RBAC et nombreux tests
spécialisés. Elle n’est pas encore une source de contrat suffisamment forte
pour une génération automatisée : les schemas, permissions effectives,
statuts, erreurs, appels frontend directs et comportements de panne ne sont
pas tous reliés par une vérification unique.

La prochaine étape de normalisation doit donc être contractuelle et
fail-closed, avant toute automatisation de consommation. Aucun MCP n’a été
proposé ni implémenté dans cet audit.

Quatre revues readonly indépendantes (inventaire OpenAPI, routes, parité
de contrat, sécurité HTTP) recoupent les mêmes P0/P1. S’y ajoutent : query
boolean vs `'true'`, champs d’erreur hors schéma (`setupUrl`, `usage`),
désaccord métadonnées/octets sur un même asset, et le fait que restore /
delete user / delete campaign / orphaned-files apparaîtraient comme des
outils ordinaires. Le YAML décrit aussi des routes REST (murs, lumières,
brouillard) que le SPA n’appelle pas — la table live passe par le socket.
`spec-coverage.py` ne compte pas les headings combinés du guide
(``GET|POST``) ; le chiffre 84 sous-estime encore légèrement la prose.
